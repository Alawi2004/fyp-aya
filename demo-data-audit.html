Function getTopUpLocations()
Demo Data Lines 554 – 591
Trigger Catch block — any DB error (incl. missing table)
When the DB query on top_up_locations fails (table doesn't exist yet or connection error), the catch block silently returns 4 hardcoded fake locations instead of an error. The fake data includes placeholder names ("Central Bus Station — Main Office", "Airport Transit Hub Kiosk"), US-format phone numbers (+1 555-01xx), and generic addresses. Passengers can see this data and assume these are real locations.
passenger-facing silent fallback fake phone numbers table may not exist
Fix Steps
  1. Create the top_up_locations table in db/featureSetup.js (or a migration) and seed real locations.
  2. In the catch block, replace res.json(FALLBACK_LOCATIONS) with res.status(500).json({ error: "Failed to fetch locations" }).
  3. Delete the FALLBACK_LOCATIONS constant (lines 554–591).

Scheduled Report Emails — Driver Performance, Vehicle Utilization, Revenue

File services/email.service.js
Function buildReportHtml()
Demo Data Lines 40 – 66
Trigger Every scheduled report email that is sent
The buildReportHtml() function contains a hardcoded sampleRows object with fake table rows for three report types. These fake rows are embedded in every scheduled report email sent to admins:

• driver-performance: Fake drivers "Karim Moussa", "Maya Salameh", "Fadi Gemayel", "Lara Abi Nader" with invented trip counts, ratings, and scores.
• vehicle-utilization: Fake buses BUS-01, BUS-03, BUS-06, BUS-08 with invented hours and distances.
• revenue: Fake routes "Route 12A", "Route 7B", "Route 3C" with invented USD amounts.

Recipients receive these as if they are real operational statistics.
email-sent-to-admins fake driver names fake revenue figures 3 report types affected
Fix Steps
  1. Accept a rows and columns parameter in buildReportHtml(reportType, reportName, rows, columns).
  2. In controllers/scheduledReports.controller.js, query the DB for the report data before calling buildReportHtml, and pass the real rows.
  3. Remove the sampleRows and headers objects from email.service.js entirely.
  4. Handle the case where the DB returns no rows (show "No data available for this period" in the email).

Permission Matrix — Hardcoded Role Fallback

File db/permissionCache.js
Export HARDCODED_MATRIX
Lines 7 – 94
Trigger DB returns 0 rows or DB connection fails
HARDCODED_MATRIX is a full role-permission map (9 roles) used as a fallback when the role_permissions table is empty or unreachable. While intentional as a safety net, it creates a risk: if the DB permissions table is accidentally cleared or never seeded, the app silently continues with static permissions that may not match the intended production configuration. The matrix is currently used by all route-level permission checks via the permissions.middleware.js.
security-relevant silent fallback affects all authenticated routes intentional but risky
Fix Steps
  1. Add a startup health-check that logs a loud warning (or blocks startup) if the DB returns 0 rows for role_permissions.
  2. Consider replacing the silent fallback with a hard 503 response when the DB permission load fails in production (NODE_ENV === 'production').
  3. Ensure featureSetup.js seeds the role_permissions table so the fallback is never triggered in a healthy deployment.
