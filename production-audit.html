📋 Executive Summary

The system has a solid architectural foundation: the permission model, auth cookie handling, 2FA/TOTP, wallet transactions, health check, and DB query safety are all production-grade. However, the driver app and several high-traffic endpoints (GPS, trips, notifications) were shipped without authentication middleware, making the current build unsafe to deploy publicly.

Fixes C-1 through C-9 are all additive — adding middleware lines or fixing one-line logic errors — not architectural rewrites. The estimated effort to resolve all Critical + High issues is 3–5 engineering days.

Verdict: Do not deploy to production until all Critical and High items are resolved.

🔴 Critical Issues Must fix before deployment

C-1
Entire Driver App has zero authentication
📄 backend/src/routes/driverApp.routes.js

Every one of the 12 driver endpoints is completely unprotected. An unauthenticated caller can start or complete trips, fire emergency alerts, scan passenger QR codes, and report delays — no token required.

router.get("/trips",              getDriverTrips);    // no auth
router.put("/trips/:id/start",    startTrip);         // no auth
router.put("/trips/:id/complete", completeTrip);      // no auth
router.post("/emergency",         sendEmergency);     // no auth
router.post("/scan-qr",           scanPassengerQr);   // no auth
router.post("/location",          updateLocation);    // no auth
// ... all 12 routes
▶ Fix

Add a router-level role guard as the very first line after creating the router:

import { requireRole } from "../middleware/permissions.middleware.js";
router.use(requireRole("driver"));
C-2
All GPS endpoints have zero authentication
📄 backend/src/routes/gps.routes.js

Anyone can write fake GPS coordinates for any trip and read all live vehicle positions. There is no token check on any GPS route.

router.post("/", sendGpsLocation);          // POST — inject fake GPS for any trip
router.get("/live", getLiveGps);            // GET  — all live positions exposed
router.get("/geofence-alerts", ...);        // GET  — geofence data public
router.get("/bus/:vehicleId", getBusGps);   // GET  — single bus GPS public
router.get("/:trip_id/latest", ...);        // GET  — latest fix public
▶ Fix
// Write endpoint — only authenticated drivers
router.post("/", requireRole("driver"), sendGpsLocation);

// Read endpoints — any authenticated user
router.get("/live",   requirePermission("live", "view"), getLiveGps);
router.get("/bus/:vehicleId", requireAuth, getBusGps);
C-3
Trip mutation endpoints have zero authentication
📄 backend/src/routes/trips.routes.js

Trip creation, status updates, and recurring schedule management are all completely public. Anyone can create or cancel trips.

router.post("/",                    createTrip);              // no auth
router.put("/:id/status",           updateTripStatus);         // no auth
router.put("/:id",                  updateTripStatus);         // no auth
router.post("/recurring",           createRecurringSchedule); // no auth
router.put("/recurring/:id",        updateRecurringSchedule); // no auth

▶ Fix
router.post("/", requirePermission("trips","create"), createTrip);
router.put("/:id/status", requirePermission("trips","edit"), updateTripStatus);
router.delete("/recurring/:id", requirePermission("trips","delete"), deleteRecurringSchedule);

Notifications endpoint has zero authentication
📄 backend/src/routes/notifications.routes.js

C-6
super_admin is blocked from admin-only vehicle pages
📄 backend/src/middleware/auth.middleware.js · backend/src/routes/vehicles.routes.js

The requireAdminOnly middleware checks role !== "admin" exactly — it does not allow super_admin. The permission middleware correctly bypasses super_admin, but requireAdminOnly is a separate, narrower guard. Result: the super admin account is locked out of vehicle docs, maintenance records, and fuel logs.

// Current — WRONG: super_admin fails this check
export const requireAdminOnly = (req, res, next) => {
  requireAuth(req, res, () => {
    if (req.user?.role !== "admin") {   // ← only "admin" passes
      return res.status(403).json({ error: "Forbidden" });
    }
    next();
  });
};
▶ Fix
export const requireAdminOnly = (req, res, next) => {
  requireAuth(req, res, () => {
    if (!["admin", "super_admin"].includes(req.user?.role)) {
      return res.status(403).json({ error: "Forbidden — admin access only" });
    }
    next();
  });
};
C-7
Ticket booking allows any passenger to impersonate any user
📄 backend/src/controllers/tickets.controller.js — line 48

The booking controller reads user_id from the request body and falls back to the JWT user only if the body field is absent. A passenger can book a ticket and have the fare debited from another user's wallet simply by passing user_id: 999 in the body.

// Current — WRONG
const user_id = req.body.user_id ?? req.user?.user_id;
▶ Fix
const PRIVILEGED = ["admin","super_admin","staff","finance_officer"];
const isPrivileged = PRIVILEGED.includes(req.user?.role);
const user_id = isPrivileged
  ? (req.body.user_id ?? req.user.user_id)
  : req.user.user_id;  // passengers always book for themselves
C-8
Admin panel defaults to mock/demo mode when env var is absent
📄 admin/src/context/AuthContext.jsx — line 4 · frontend/src/context/AuthContext.js — line 9

The frontend-only flag is inverted: it evaluates to true (mock mode) unless VITE_FRONTEND_ONLY is explicitly set to the string "false". In a fresh deployment where that env var is absent, session management, 2FA setup, and login audit features silently return hardcoded fake data with no warning to the operator.

// Current — WRONG: defaults to true (mock mode)
const FRONTEND_ONLY = import.meta.env.VITE_FRONTEND_ONLY !== "false";
▶ Fix — invert the default
// Correct: only enable mock mode when explicitly requested
const FRONTEND_ONLY = import.meta.env.VITE_FRONTEND_ONLY === "true";

Apply the same fix to EXPO_PUBLIC_FRONTEND_ONLY in the React Native context.

C-9
JWT_SECRET is a placeholder — every token is forgeable
📄 backend/.env

The .env file contains JWT_SECRET=CHANGE_ME_GENERATE_A_LONG_RANDOM_SECRET. If this placeholder value is deployed unchanged, any attacker who knows it can sign their own tokens with any role claim and gain full administrative access to the system.

▶ Immediate action — generate a real secret
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
# e.g. → 7f4d9c2e1a8b6f3e5c9d2b1a7f4d8c6e3f9a2b1d...

After updating the secret, all existing tokens are automatically invalidated — users will need to log in again. This is the correct behaviour.

GPS controller doesn't verify the driver owns the trip
📄 backend/src/controllers/gps.controller.js

H-3
Content-Security-Policy is explicitly disabled
📄 backend/src/app.js — line 78

contentSecurityPolicy: false is set in the helmet config. A CSP is the primary browser-side defence against XSS: without it, any injected script runs with full page privileges. The comment acknowledges this as a TODO.

▶ Fix — start with a permissive policy and tighten later
app.use(helmet({
  contentSecurityPolicy: {
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc:  ["'self'", "https://unpkg.com"],
      imgSrc:     ["'self'", "data:", "https://*.tile.openstreetmap.org"],
      connectSrc: ["'self'", "ws:", "wss:"],
    },
  },
  crossOriginResourcePolicy: { policy: "cross-origin" },
}));
H-4
No CSRF protection on cookie-authenticated routes
📄 backend/src/app.js

Auth uses httpOnly cookies. A malicious third-party page visited by a logged-in admin can make cross-origin POST/DELETE requests and the browser automatically attaches the session cookies. The CORS allowlist helps but does not protect against CSRF from same-browser attacks. SameSite: strict is set on cookies which provides partial protection, but can break legitimate flows from external links.

▶ Fix — double-submit cookie pattern
// On login: set a non-httpOnly CSRF cookie
res.cookie("csrf_token", cryptoToken, { httpOnly: false, sameSite: "strict", secure: isProd });

// On state-changing requests: validate header matches cookie
app.use((req, res, next) => {
  if (!["POST","PUT","PATCH","DELETE"].includes(req.method)) return next();
  const header = req.headers["x-csrf-token"];
  const cookie = req.cookies.csrf_token;
  if (!header || header !== cookie) return res.status(403).json({ error: "Invalid CSRF token" });
  next();
});
H-5
Admin panel stores user object in localStorage
📄 admin/src/context/AuthContext.jsx — line 86

The user's role, email, and user_id are written to localStorage and readable by any JavaScript on the page. If a future XSS vulnerability is introduced, an attacker immediately knows the target's admin role and can tailor the attack. Access tokens remain safe in httpOnly cookies.

▶ Fix — use sessionStorage or React state only
// Replace localStorage with sessionStorage (clears on tab close)
// or keep the user entirely in React state (no persistence needed — the
// cookie keeps them logged in across page refreshes anyway)
sessionStorage.setItem(USER_KEY, JSON.stringify(u));
H-6
No pagination on large list endpoints
📄 Multiple controllers

The following endpoints return all rows from the database with no row cap. With thousands of records these requests will cause multi-second query times, backend timeouts, and OOM conditions on the API server:

GET /api/tickets          → all tickets with 3-table JOIN, no LIMIT
GET /api/gps/live         → all live GPS points
GET /api/notifications    → all notifications
GET /api/audit-logs       → all audit entries (potentially millions of rows)
▶ Fix — enforce a maximum page size
const page  = Math.max(1, parseInt(req.query.page)  || 1);
const limit = Math.min(100, parseInt(req.query.limit) || 50);
const skip  = (page - 1) * limit;
// then append to query:
// ORDER BY ... OFFSET @skip ROWS FETCH NEXT @limit ROWS ONLY
H-7
Auth middleware does not check token revocation
📄 backend/src/middleware/auth.middleware.js — line 15

jwt.verify() only checks the signature and expiry. It does not check whether the session was revoked (e.g., forced-logout by an admin or the user themselves). After a session is revoked in the UI, the access token (valid for up to 15 more minutes) still works on every API endpoint.

▶ Fix — check session table on each request
// In requireAuth, after jwt.verify():
const sessionOk = await pool.request()
  .input("token_hash", sql.NVarChar, hashToken(token))
  .query("SELECT 1 FROM user_sessions WHERE token_hash = @token_hash");
if (!sessionOk.recordset.length)
  return res.status(401).json({ error: "Session revoked" });

H-10
Email provider is a personal Gmail account (500/day hard cap)
📄 backend/.env — SMTP config

The SMTP config uses a personal Gmail account with an app password. Gmail enforces a hard cap of 500 outbound emails per day. Password-reset emails, scheduled reports, and push notification fallbacks will silently fail once the cap is hit. This is noted in a comment in the .env itself.

▶ Switch to a transactional email provider
SendGrid:  100 emails/day free  → SMTP_HOST=smtp.sendgrid.net
Mailgun:   5,000/month free      → SMTP_HOST=smtp.mailgun.org
AWS SES:   $0.10/1,000 emails   → use @aws-sdk/client-ses

🟡 Medium Priority Issues Fix before public launch

M-1
requireAdmin middleware passes both admin and staff — potential role confusion
📄 backend/src/middleware/auth.middleware.js — line 26

The requireAdmin middleware allows both admin and staff roles through. It is not currently wired to any route (routes use requireAdminOnly or requirePermission), but its existence creates confusion and a future developer might use it incorrectly. Rename it to requireAdminOrStaff or remove it entirely.

M-2
No vehicle capacity check in ticket booking
📄 backend/src/db — book_ticket stored procedure

The book_ticket procedure checks whether a specific seat is already taken, but does not compare total booked seats against vehicles.capacity. A 45-seat bus can receive unlimited bookings as long as different seat labels are used.

▶ Fix — add a capacity guard inside the stored procedure
IF (SELECT COUNT(*) FROM tickets WHERE trip_id = @p_trip_id AND status != 'cancelled') >=
   (SELECT v.capacity FROM trips t JOIN vehicles v ON v.vehicle_id = t.vehicle_id WHERE t.trip_id = @p_trip_id)
BEGIN
  ROLLBACK;
  RAISERROR('Trip %d is fully booked', 16, 1, @p_trip_id);
  RETURN;
END
M-3
No driver/vehicle availability check when creating trips
📄 backend/src/controllers/trips.controller.js

Trip creation does not verify that the assigned driver is active and has a valid, unexpired licence, that the vehicle is in active status (not maintenance), or that there are no overlapping trips for the same driver or vehicle. The /trips/conflicts endpoint exists for detection but nothing blocks the double-booking on insert.

M-4
Email HTML templates are not XSS-sanitised
📄 backend/src/services/email.service.js

Report names and system setting labels are interpolated directly into HTML email strings without escaping. If a report type or label contains <img onerror=...>, that markup is delivered in the email body.

▶ Fix — add a minimal HTML escape before template injection
const esc = s => s.replace(/[<>&"']/g, c =>
  ({ '<':'&lt;','>':'&gt;','&':'&amp;','"':'&quot;',"'":'&#39;' }[c]));
const safeLabel = esc(REPORT_LABELS[reportType] ?? reportName);
M-5
console.error calls scattered across production controllers
📄 Multiple controllers

Many controllers use console.error(err) which writes full stack traces — including internal file paths, table names, and SQL error text — to stdout. In a containerised environment these appear in application logs and may be surfaced to monitoring dashboards. Replace with a structured logger.

▶ Fix — use pino or winston
import pino from "pino";
const logger = pino({ level: process.env.LOG_LEVEL ?? "info" });
// Replace: console.error(err)
// With:    logger.error({ err }, "wallet recharge failed");
M-6
Mobile app falls back to unencrypted AsyncStorage for auth tokens
📄 frontend/src/utils/secureStorage.js — line 37

When SecureStore.setItemAsync throws, auth tokens are silently written to plain AsyncStorage (not encrypted on Android). This fallback is intended for Expo Go, but if a production device encounters an unexpected SecureStore failure, tokens are stored in plaintext with no alert.

▶ Fix — log a warning on fallback
async function _secureSave(key, value) {
  try {
    await SecureStore.setItemAsync(key, value, { keychainAccessible: SecureStore.WHEN_UNLOCKED_THIS_DEVICE_ONLY });
  } catch (e) {
    console.warn("[secureStorage] SecureStore unavailable, falling back to AsyncStorage:", e.message);
    await AsyncStorage.setItem(key, value);
  }
}
M-7
Unencrypted AsyncStorage used for generic data — verify no secrets flow through it
📄 frontend/src/utils/storage.js

The generic storeData / getData helpers store everything in unencrypted AsyncStorage. Audit every call site to confirm no sensitive values (PII beyond display name, tokens, session data) are stored through this utility instead of secureStorage.js.

M-8
Scheduled report emails have no retry logic
📄 backend/src/services/email.service.js

If SMTP is temporarily unavailable, the report is logged as failed and not retried until the next scheduled cycle (30 minutes later). For compliance and business continuity, implement at least 3 retry attempts with exponential backoff before marking a delivery as permanently failed.

M-9
No audit trail for sensitive write operations
📄 Multiple controllers

Login audit logging is thorough. However, the following operations currently produce no audit record — making fraud detection and compliance reviews impossible:

Wallet freeze / unfreeze
Manual wallet balance adjustments
User suspension / restoration
Vehicle document updates (registration, insurance)
Trip cancellation

The audit_logs table already exists in the schema. Wire in audit writes to these controller functions.

M-10
mockStops.js may be bundled in the production app
📄 frontend/src/utils/mockStops.js

A file named mockStops.js exists in the production source tree. Verify it is used only in tests or behind a FRONTEND_ONLY guard. Static mock data shipped in a production bundle inflates bundle size and can cause confusing UX if accidentally rendered.

M-11
Permission cache has no automatic expiry / TTL
📄 backend/src/db/permissionCache.js

The permission matrix is loaded from the DB once at startup (or first request) and cached indefinitely in memory. If an admin changes a role's permissions in the Roles page, those changes won't take effect until the server restarts or refreshPermissionCache() is called manually — which no API endpoint does automatically after a role edit.

▶ Fix — add a 5-minute TTL
let cacheExpiry = 0;
export async function getMatrix() {
  if (Date.now() > cacheExpiry) {
    cache = await loadFromDb();
    cacheExpiry = Date.now() + 5 * 60 * 1000;
  }
  return cache;
}
